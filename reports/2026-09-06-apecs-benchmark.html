Trait count

The five-trait cliff, and who pays it

Nanoseconds per entity visit against the number of distinct traits a program uses, one trait count per process — sweeping inside one process lets earlier traits pollute the dispatch site and manufactures a cliff whether or not it is there. Two of the four libraries charge for trait count, and they break in different places: becsy at the fifth trait, koota at the second.

Capability

Iterating in key order, every frame

100 000 entities, microseconds per frame, log scale. bitECS and becsy ship no sorting, so their honest cost is the hand-written one: copy the ids out and sort them. Every apecs frame includes the world.step() a real frame pays — the dirty check is tick-based, and a view settles only once the tick has moved past the writes that built it.

keys never change 1% of keys change per frame

Sorted iteration is free; sorting is not. On a clean frame the rows are already in key order, so there is no gather and no side array to walk — 29.6× faster than apecs's own sortBy. When 1% of keys drift, orderBy extracts the keys, sorts, and applies the permutation to every column: 1.2× the hand-written sort, which moves one id array where apecs moves five columns of real data.

The guarantee is per archetype Rows are in key order within each matching archetype, not across them — chunk boundaries are archetype boundaries, and a merge cannot cross one without materialising. sortBy remains the answer when the order must be total.
Footprint

Bytes per entity

A world of entities carrying Position + Velocity — two f32 fields each, so 16 bytes is the payload. Everything above it is ids, masks, archetype bookkeeping and query caches. Measured as absolute resident bytes at five world sizes and least-squares fitted; the check that the fit works is that the hand-written baseline lands on 16.

Reading the fit It spans an empty world, so a fixed cost that moves between builds leaks into the slope. The marginal bytes between the two largest sizes cannot: 16.0 for hand-written, 36.9 for apecs, 239.8 for bitECS, 304.7 for koota, 153.4 for becsy.

Method

What would have made this wrong

One process per library, per benchmark

Four ECS libraries in one isolate make the shared iteration call sites megamorphic, and V8 deoptimises whichever warmed up second — a larger effect than most of the differences being measured.

A fairness census before any timing

Every library must match the same entity count on every query-shaped benchmark or the run aborts. It caught apecs's Not() silently ignoring all but its first argument, and becsy's perf build silently creating only some of the entities asked for.

Minimum of 3 full runs

One pass is not trustworthy on a laptop: across runs some competitor cells moved by tens of percent while apecs's moved under 2%. Worst spread observed here: packed_1 · koota · raw at 172%.

Production builds only

apecs from its built dist/ with __DEV__ compiled out; becsy from its perf build, whose default carries runtime validation.
