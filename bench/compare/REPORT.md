# apecs vs. the JS/TS ECS field

> Generated by `node report.mjs` from `results.json`. Measured 2026-09-06 on Apple M1, Node v20.19.0 (darwin arm64).

## What is being compared

| Library      | Version             | Design                                                                                                                                    |
| ------------ | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| hand-written | hand-written        | Typed arrays and index arithmetic. No entity ids, no queries, no structural change.                                                       |
| apecs        | 0.1.0 (dist)        | Archetype + SoA typed columns. `each` is the idiom; `chunks` hands back the raw arrays, `accessor` a resolved field for access by handle. |
| bitECS       | 0.4.0               | Sparse sets; components are user-owned typed arrays indexed by entity id. No archetypes, no ergonomic tier.                               |
| koota        | 0.6.6               | Archetype-ish query cache over SoA stores held in plain JS arrays (not typed arrays).                                                     |
| becsy        | 0.15.5 (perf build) | Archetype + typed columns, but scheduler-first: every figure includes one `world.execute()` frame.                                        |

apecs is measured from its built `dist/` — the same bytes a user installs, with `__DEV__` assertions
compiled out (verified by `npm run check:bundle`). becsy is measured from its `perf` build for the
same reason: its default build carries runtime validation and benchmarking it would be dishonest.

## Method, and the two things that would have made this report wrong

**One process per (library, benchmark).** Loading four ECS libraries into one isolate makes the shared
call sites in the iteration path megamorphic, and V8 then deoptimises whichever library warmed up
second. That effect is larger than most of the differences being measured.

**A fairness census, run before any timing.** Every library must match the _same number of entities_
on every query-shaped benchmark, or the run aborts. This is not a formality — it caught two real
problems that would each have produced a fake result:

- `Not()` in apecs takes exactly one operand, unlike `Or()`, and silently ignored the other twelve
  arguments the adapter passed it. The `mixed_query` benchmark was matching 96 153 entities instead
  of 49 998.
- becsy's `perf` build has its assertions compiled out. On the default `maxShapeChangesPerFrame` it
  silently creates only _some_ of the entities you ask for, and every query built on them comes back
  short — with no error anywhere. Three of becsy's benchmarks were quietly iterating nothing.

Structural benchmarks get the same treatment: `verify-structural.mjs` proves the add/remove work
actually changes state, and because becsy defers structural changes to the frame boundary,
`verify-becsy-coalesce.mjs` proves it is not collapsing an in-frame add+remove into nothing
(3588.8µs in-frame vs 3665µs across alternating frames — it is doing the work).

Every figure is the mitata average over a ≥1s CPU-time sample after an explicit warmup, and each
cell is the **minimum across 3 full runs**. One pass is not trustworthy on a laptop: across runs some
competitor cells moved by tens of percent while apecs's moved under 2%, which is background load
rather than a property of any library (worst observed spread: packed_1 · koota · raw at 172%).

What each row is measuring:

- **Iterate one trait** (`packed_1`) — 5 000 entities, five traits each, one arithmetic pass over one trait. Best-case iteration. One archetype, no misses, nothing to skip.
- **Five systems in a row** (`packed_5`) — 1 000 entities, five traits each, five passes — one per trait. Per-query fixed cost. Five short scans expose setup overhead a long scan hides.
- **Move 100 000 entities** (`simple_iter`) — 100 000 entities, Position + Velocity, one integrate pass (SPEC §12.1). The real-world hot loop. This is the number that matters most.
- **Iterate across 26 archetypes** (`frag_iter`) — 100 000 entities spread over 26 archetypes, iterate the one shared trait. Fragmentation cost. Archetype designs pay per archetype; sparse-set designs do not.
- **Spawn and despawn** (`entity_cycle`) — Spawn 100 000 entities with two traits, then despawn all of them. Entity churn: id allocation, row insert, row release, free-list reuse.
- **Add and remove a trait** (`add_remove`) — Add a trait to 100 000 existing entities, then remove it from all of them. Structural change. Archetype designs move a row; sparse-set designs flip a bit.
- **Query with exclusions** (`mixed_query`) — 26 archetypes; query the shared trait while excluding 13 of the 26 fragment traits. Negation. Archetype matching resolves it once at query build; per-entity designs re-test every entity.
- **Look up by entity handle** (`random_access`) — Read and write one field on 100 000 entities in shuffled order, by entity handle. Per-entity access by handle. Only ~20% of the cost is the shuffled order — the rest is the accessor call itself, and it is there in sequential order too.

## Memory

Bytes per entity for a world of entities carrying Position + Velocity — two `f32` fields each, so
**16 bytes is the actual payload**. Everything above 16 is what the library charges for ids, masks,
sparse sets, archetype bookkeeping and query caches.

Measured as absolute resident bytes at five world sizes, least-squares fitted — _not_ as a
before/after delta, which subtracts two heap readings taken at different points in the collector's
life and is dominated by when it happened to compact. Measured that way, 100 000 entities came out
_smaller_ than 10 000. The check that the fit works: the hand-written baseline must land on 16.

| Library      | Bytes/entity | Overhead above payload    |
| ------------ | ------------ | ------------------------- |
| hand-written | 16.0         | — (this _is_ the payload) |
| apecs        | 38.1         | 2.4× payload              |
| bitECS       | 236.7        | 14.8× payload             |
| koota        | 293.8        | 18.4× payload             |
| becsy        | 154.4        | 9.6× payload              |

At 1 000 000 entities that is 38 MB for apecs against 237 MB for bitECS and 294 MB for koota.

As a cross-check the fit is not being steered by its empty-world point: the _marginal_ bytes between
the two largest world sizes are 16.0 for hand-written, 36.9 for apecs, 239.8 for bitECS, 304.7 for koota, 153.4 for becsy.

## The finding that mattered most: an ergonomic tier that fell off a cliff at five traits

V8's inline caches hold four shapes before going megamorphic. Every library here that offers a
per-entity ergonomic accessor dispatches through some internal call site, and once a program uses
enough distinct traits with it, that site can tip over. apecs used to. It no longer does.

ns per entity-visit, ergonomic tier, **one trait-count per process** — sweeping `k` inside a single
process lets earlier shapes pollute the dispatch site, which manufactures the cliff whether or not
`k` causes it:

| distinct traits             | 1    | 2    | 3    | 4    | 5    | 6    | 8    |
| --------------------------- | ---- | ---- | ---- | ---- | ---- | ---- | ---- |
| apecs                       | 2.2  | 1.9  | 1.9  | 1.9  | 1.9  | 1.9  | 2.0  |
| bitECS                      | 1.5  | 1.5  | 1.6  | 1.5  | 1.5  | 1.5  | 1.6  |
| koota                       | 21.2 | 32.0 | 32.1 | 32.0 | 32.1 | 32.0 | 32.0 |
| becsy                       | 5.5  | 9.5  | 9.8  | 10.3 | 38.6 | 38.2 | 37.9 |
| apecs, before the fix below | 2.2  | 1.9  | 2.7  | 2.9  | 12.6 | 38.3 | 42.8 |

- **apecs is now the fastest ergonomic tier measured, at every trait count** — flat at ~1.9 ns, where
  it used to reach 42.8 ns at eight traits. bitECS is faster still at ~1.5, but that is its raw
  array API; it has no ergonomic tier to compare.
- **becsy** still has the cliff, in the same place, 3.7×.
- **koota** degrades only 1.5×, but starts an order of magnitude behind.
- **bitECS is immune** — flat at ~1.5 ns. It has no per-component dispatch to go megamorphic.

### What the cliff actually was

Not the shape count as such. apecs generates a driver per query and an accessor class per trait so
that the hot sites inside them stay monomorphic — SPEC §12.2 rule 2. The generated sources were
identical text, and **V8 keys its compilation cache on source text**: every one of those `new Function`
calls returned the same `SharedFunctionInfo`, so all the closures shared a single feedback vector.
The per-query codegen was real and the specialisation it bought was not.

The fix is a marker comment that makes each generated source unlike any other (`distinct()`,
src/core/codegen.ts). Nothing else changed — same drivers, same cursor classes, same walk. It moved
`packed_5`'s ergonomic tier from 33.0 µs to 9.8 µs and left every one-trait benchmark where it was.

The lesson generalises past this library: a per-shape codegen strategy is only as good as the
distinctness of the text it emits, and the failure is invisible in every measurement that uses one
shape at a time.

**apecs's `chunks` tier is completely immune** and is the fastest thing in this report — flat at
0.96/0.97/0.98/0.98 ns/entity through eight traits, against bitECS's ~1.5.

Per-call costs, for sizing systems that run over small archetypes
(`node scaling.mjs`): `each` is 167 ns fixed + 1.79 ns/entity;
`chunks` is 36 ns fixed + 0.96 ns/entity.

## Capability comparison: sorted queries

Sorting is where apecs claims a feature the field mostly lacks. bitECS and becsy ship none; koota has
`QueryResult.sort()`, which re-sorts on demand. apecs ships two answers: `sortBy` keeps the order in a
side array and hands out `each`, while `orderBy` (SPEC §6.8) permutes the archetype rows themselves, so
the order _is_ the storage layout and `chunks` keeps working. 100 000 entities iterated in sorted order
every frame, microseconds:

|                                    | keys never change | 1% of keys change per frame |
| ---------------------------------- | ----------------- | --------------------------- |
| apecs `orderBy` + `chunks`         | 89                | 1636                        |
| apecs `orderBy` + `each`           | 197               | 1784                        |
| apecs `sortBy` + `each`            | 2626              | 2915                        |
| koota `sort()`                     | 25328             | 17491                       |
| hand-written `Array.sort` + gather | 1415              | 1402                        |

Every apecs frame here includes the `world.step()` a real frame pays. The dirty check is tick-based
(SPEC §8.3): a view settles only once the tick has moved past the writes that built it, and the previous
version of this benchmark left it out — which measured `sortBy` re-sorting every frame in the regime
that exists to show it does not.

**`orderBy` is the headline.** On a frame where no key moved it costs 89 µs — 285× faster than
koota, 15.9× faster than sorting an id array by hand, and 29.6× faster than apecs's own `sortBy`. There is
no gather and no side array to walk: the rows are already in key order, so the frame is one dirty check
and a plain chunk walk — 0.89 ns/entity, against the 0.96 ns/entity an _unsorted_ `chunks` walk costs.

**The trade is on the frames that do sort.** With 1% of keys drifting, `orderBy` pays a real resort —
key extraction, an adaptive sort, then the permutation applied to every column — and lands at
1636 µs, 1.2× the hand-written sort, which moves one id array where apecs moves five columns of
real data. Sorted _iteration_ is free; sorting is not. It is still 10.7× faster than koota, which
re-sorts unconditionally whether or not anything moved.

**`sortBy` is the one to watch.** 2626 µs on a _clean_ frame, against 89 µs for `orderBy`, because the
materialised walk is the cost even when the order is cached:

- Iterating the same query linearly costs 2 ns/entity. Iterating it sorted costs 38.5 ns/entity — **19×**.
- A hand-written gather over an identical precomputed order costs 1.3 ns/entity, so the gap is not memory locality; it is ~37 ns/entity of overhead inside the sorted iteration driver.
- `sorted.entities()` on a view whose keys were **never touched** costs 5.4 ns/entity, and that cost is flat at every world size (5.77 / 5.34 / 5.24 ns/entity at 1 k / 10 k / 100 k). It is O(n).

SPEC §12.1 budgets `sorted-static` at **zero work** — "one `lastWriteTick` compare per matching
archetype." `sortBy` does not meet it: its clean-frame cost is linear in entity count at every size.
`orderBy` does, and that is what it was built for — it is the same 0.89 ns/entity as an unsorted walk,
so the ordering itself is genuinely free. The remaining choice is a semantic one: `sortBy` when the
order must be total across archetypes, `orderBy` when it need only hold within each (SPEC §6.8).

## What the accessor work changed

**Look up by entity handle** (`random_access`) was the worst figure in the previous report — 5 971 µs, 43× behind bitECS. Two
changes landed since: a cleanup of `World#get`/`#set`, and `world.accessor(field)`, a handle that
resolves a field once and keeps a table indexed by archetype id.

|                                              | ns/entity | `random_access` |
| -------------------------------------------- | --------- | --------------- |
| `world.get` + `world.set`, before            | 51.9      | 5 971 µs        |
| `world.get` + `world.set`, after the cleanup | 26.5      | 2613 µs         |
| `world.accessor`                             | 14.9      | 1393 µs         |

That is **4.3× on the benchmark**, and it closes the gap to bitECS from 43× to 10.2×.
It does **not** change the placing: apecs is still 4th of four here, behind bitECS (137 µs), koota (219 µs), becsy (737 µs).
And it cannot reach bitECS: two dependent lookups plus paged columns against one flat array load
is inherent to an archetype design. The remaining question is whether the gap to koota — whose
stores are id-indexed, so its raw tier is a single array index — is worth closing further.

**A correction to the estimate that motivated this.** The earlier prototype predicted 8.8 ns/entity.
That figure compared a _fused_ read-modify-write against a two-call `get` + `set`, and used a
one-entry cache that collapses to 27 ns once the world fragments — it was not a like-for-like
target. Measured like for like, a bare dense-table prototype costs 12.7 ns, and 12.9 ns once it also
does the change-tick stamping a correct `set` owes. The shipped accessor is 14.9 ns — within 2 ns
of the practical ceiling for a design that does not degrade under fragmentation.

The iteration path was not touched by the accessor work, and the cliff fix did not move it
either — a one-trait query has no shape collision to lose. `each` is still
167 ns + 1.79 ns/entity, `chunks` still 36 ns + 0.96 ns/entity.

## Reproducing

```bash
cd bench/compare && npm install
node run.mjs                                     # one pass -> results.json
node merge.mjs results.json a.json b.json c.json # per-cell minimum across passes
node report.mjs                                  # -> REPORT.md
```

Supplementary measurements in `findings.json` each name the script that reproduces them.
